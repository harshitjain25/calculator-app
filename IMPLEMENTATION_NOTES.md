# Implementation notes

- **Stored state:** `_input` is a string so partial input such as `5.` survives; `_firstOperand` is a nullable double; `_operator` is a nullable visual operator; `_waitingForOperand` distinguishes the display of the first operand from actual second input; `_showingResult` determines fresh input behavior; `_error` holds a recoverable message; `_history` holds expression/result entries for this session.
- **Derived values:** the numeric second operand is parsed only when needed. Expression/status text, history count, and button styling come from existing state. They do not need separate mutable fields.
- **Operator selection:** stores the current value and operator, then waits for second input. Repeated operators before second input replace the operator. An operator after second input reports that equals is required, preserving the unfinished operation.
- **Calculation:** validate completeness and zero division, use a switch with Dart arithmetic, validate finite/range constraints, format the result, and add one successful history entry. No arbitrary strings are evaluated.
- **Decimals:** input begins with `0.` when decimal is pressed first. A second decimal is rejected without changing input. Results are rounded to 12 significant digits, normalized through double parsing, and whole results use zero fractional digits. Small results may use scientific notation.
- **Recovery:** errors leave the calculation intact. Digits, decimal input, or backspace dismiss the message so input can be corrected. AC resets input, first operand, operator, both flags, and error. It intentionally retains history. Failed calculations never enter history.
- **History:** newest entries appear first in a lazily built ListView in a modal bottom sheet. Tapping an entry resets the pending operation and displays its result, allowing an operator to reuse it. Clear History clears only the list. Nothing is persisted after the app session.
- **Backspace:** removes one character during entry, including a decimal point; empty/sign-only values normalize to zero. While awaiting the second number, it leaves the pending operation alone. Hold clears the current entry while retaining a pending operator. A displayed result is cleared entirely because editing scientific notation would be confusing.
- **Alternative:** an expression parser with a separate controller could support chains and precedence, but introduces parsing and additional state. One StatefulWidget and explicit helper methods make this assignment easier to explain.
- **Trade-off:** doubles and 12-significant-digit formatting keep the implementation small but do not provide exact arbitrary-precision decimal arithmetic. Inputs have at most 12 digits and result magnitude must be below 10¹²; rounding and tiny scientific-notation results are possible. Range checks prevent silently showing infinity. History remains unbounded for the session, favoring simplicity over a retention policy.
- **Accessibility:** meaningful semantic button labels, a live display/error announcement, Material contrast colors, explicit operator symbols, at least 48-pixel tap targets, scalable text, and scrolling on short screens. Verify TalkBack manually; widget tests cannot establish its real behavior.
- **Performance:** setState rebuilds this small page; there is no expensive parsing or external I/O. ListView.builder creates visible history rows as needed. History insertion at the front is O(n), acceptable for typical assignment sessions.
- **Evidence:** widget tests cover all eight integer/decimal arithmetic cases, incomplete equals, zero division and recovery, operator replacement, duplicate decimals, backspace/hold, fresh input, history reuse/clear, input limits, large results, and small-screen enlarged-text layout. See TESTING.md for manual cases. Record actual command outcomes separately; manual results are deliberately blank.

## Graduate extension: chained operations

This calculator intentionally uses a two-operand model and does not implement Multiple Operations as a selected feature. If chains were added, sequential evaluation of `2 + 3 × 4` would evaluate `(2 + 3) × 4` and produce 20. Normal operator precedence evaluates `2 + (3 × 4)` and produces 14. Precedence requires a different expression/state design, such as a token list and a parser or operator/operand stacks, instead of one stored operand and one operator.
